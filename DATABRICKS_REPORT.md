# Databricks in this project: a plain-language rundown

## The short version

Databricks is the project's data engine and database. The web app itself is a small Node.js service, but it asks Databricks to look up facilities, compare their service information with reviewed evidence, and return nearby results. The data is not downloaded into the browser. The browser sends a search to the app, and the app sends a SQL request to a Databricks SQL warehouse.

Think of it this way: the web page is the search form, the Node.js backend is the messenger and traffic controller, and Databricks is the filing room plus the search and ranking machinery.

## What happens when someone searches

1. The user enters a place and a care need. The browser sends them to the backend at `/api/referral`.
2. The backend asks Databricks for its service catalog (for example MRI, dialysis, or emergency department). That catalog is cached in the backend for five minutes.
3. The backend interprets the care need. Obvious emergency symptoms take a local emergency route. Otherwise, when configured, OpenAI maps the wording to a catalog service; without an API key, exact catalog terms can still work.
4. For a normal live search, the backend calls `workspace.saboot.rank_referrals(location, service)` for fitted rankings. General care and services awaiting verified labels use `workspace.referral_verification.search_referrals(location, service)`. It binds the location and service as SQL parameters, waits for the SQL statement to finish, and reads the returned JSON.
5. The browser displays the returned facility groups, distances, service claims, source links and evidence. Databricks returns a compact result payload rather than sending the full source tables to the browser.

Databricks authentication is handled by the Databricks App service principal when hosted. For local development, the backend can use a Databricks CLI profile. The SQL warehouse is selected by `WAREHOUSE_ID` in `app.yaml` (with a code fallback).

## What the live SQL search reads and does

The directory fallback is in [`databricks/referral_search.sql`](databricks/referral_search.sql). It reads stored Unity Catalog tables and views, including the Virtue facilities and India Post PIN directory, plus project tables for city origins, location checks, service claims, and reviewed source evidence.

In everyday terms, the query:

- Cleans up the typed location and tries to find a usable starting point. It can use a known city centre, a cluster of Virtue facility coordinates for a city, an India Post locality/district/PIN location, or coordinates typed by the user.
- Finds facilities with a matching service claim. For emergency and general outpatient searches it also looks for relevant phrases in facility descriptions and removes some clearly negative phrases.
- Checks facility coordinates and measures distance from the search origin. It looks within 100 km and withholds distance ranking for flagged location conflicts.
- Adds matching evidence from external evidence and the reviewed `frontend_source_signals` table.
- Groups and ranks results into nearby baseline results, stronger evidence, leads, and exclusions. A listing or historical report is evidence to review; it is not proof the facility has an open slot today.
- Packages the result as JSON for the app.

The service catalog is generated by [`databricks/referral_service_catalog.sql`](databricks/referral_service_catalog.sql). It defines the service labels, scope descriptions and keywords used for intake. Supported specialty services are checked against `service_alias_config`; emergency care and general outpatient assessment are also included.

## What is live versus prepared ahead of time

| Item | When it is fetched or created | What that means |
| --- | --- | --- |
| Service catalog | Read from Databricks on first use and then cached for five minutes per running backend | Changes to the catalog may take a few minutes to show up in an already-running app. |
| Ordinary facility search | Queried from Databricks for each search | Current contents of the underlying tables/views are queried at search time. “Live” here means a fresh directory query, not a real-time check with the hospital. |
| Reviewed evidence | Read from stored Databricks evidence tables as part of the search | It remains the last reviewed/imported information until a researcher updates it. |
| Website, directory, map and search collection | Run separately by an operator using `tools/enrichment.py` | These external sources are not fetched automatically during a normal user search. Results start as leads for review. |
| Optional Google Places lookup | Operator command only | Place IDs/status are for ephemeral operator review; Google Places content is excluded from the serving evidence table. |
| Free-text care interpretation | OpenAI is called when configured and needed for a search | This is separate from the facility data query. If not configured, exact service terms still work. |
| Page translation | OpenAI is called when the translation endpoint is used | It does not populate or preprocess facility data. |

The hosted backend checks the Databricks service catalog at startup.

## What preprocessing is visible in this repository

There is project-specific preprocessing and evidence preparation in the checked-in code, but the repository does not show how the original Virtue Foundation dataset was first collected or transformed before it became available in Unity Catalog. The search relies on already-existing tables/views such as `facilities`, `v_service_best_claims`, `facility_location_flags`, and `service_claims`; their upstream build steps are not included here.

The visible preparation steps are:

- **Location cleanup and resolution:** SQL trims/lowercases the search text, normalizes spaces, parses city/state and coordinates, resolves PINs through India Post rows, estimates locality centroids, and rejects coordinates outside India bounds. It avoids choosing a PIN cluster when the result is ambiguous.
- **Facility/service evidence matching:** the query uses prepared service-claim records and, for two general care settings, searches facility text fields for phrases. It excludes some phrases that say care is absent, referred elsewhere or only planned.
- **Distance and conflict handling:** valid coordinates are filtered to India, straight-line distances are calculated, and known conflicting facility locations are excluded from normal distance ranking.
- **External evidence collection:** `tools/enrichment.py` can collect official-site keyword excerpts, public directory rows, map-place records and limited web-search leads. It applies source/robots checks for web requests and labels records as `lead`; collection is deliberately separate from serving searches.
- **Human review and import:** an operator confirms the exact campus, service, source and rationale, then uploads JSONL to a Unity Catalog volume. [`Load reviewed referral evidence.py`](databricks/Load%20reviewed%20referral%20evidence.py) validates IDs, source type, URL, dates and review status, deduplicates records, and in Apply mode merges them into `frontend_source_signals`.


## What not to read into the results

- A fresh Databricks query does not mean the source data is current to today.
- Website claims, directories, news articles, maps and old service reports do not establish present-day availability or referral acceptance.
- The ranking is a way to organize claims and evidence for a person to check; it is not a clinical recommendation or a confirmed appointment.
- Data checks and query rules can reduce bad matches, but the upstream provenance and full original-dataset cleaning process are not documented in this repository.

## Main files to inspect

- [`backend/server.mjs`](backend/server.mjs): handles browser requests and routes live searches.
- [`backend/referrals.mjs`](backend/referrals.mjs): calls the catalog, model ranking and directory functions.
- [`backend/databricks.mjs`](backend/databricks.mjs): Databricks authentication, SQL statement submission and polling.
- [`databricks/referral_search.sql`](databricks/referral_search.sql): live location resolution, matching, distance and ranking logic.
- [`databricks/referral_service_catalog.sql`](databricks/referral_service_catalog.sql): catalog of searchable service types.
- [`tools/enrichment.py`](tools/enrichment.py): separate operator-run source collection.
- [`databricks/Load reviewed referral evidence.py`](databricks/Load%20reviewed%20referral%20evidence.py): validation and import of reviewed leads.
- [`databricks/Explore live referrals.py`](databricks/Explore%20live%20referrals.py): notebook interface to the same live search function and the directory fallback.
